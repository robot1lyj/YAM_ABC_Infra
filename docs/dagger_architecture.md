## 产品交付原则（2026-09-14）

长期维护两个产品：设备与采集平台、独立数据集平台。前者覆盖连接、初始化、调试、四模式、录制、暂停及恢复；后者覆盖导入、审核、分类、转换、归档及回读。两者共用原始数据合同，不复制机械臂控制或训练逻辑。

完整可靠首先是完整失败流程：说明哪个模块失败、机械臂现在是什么状态、哪些操作仍可用、如何恢复。检查集中在设备、进程、模型和存储边界，不反复叠加校验、不静默回退、不自动重试运动。软件暂停不能替代实体急停。

### 局域网访问与跨平台交付

设备与采集平台默认端口8766，IPC入口为 `http://192.168.110.140:8766`；数据集平台默认8767。浏览器不用安装SDK，页面/API同源，明确监听地址和Host白名单。多个页面只能有一个操作会话，旁观页不能抢占心跳；任何页面仍可发暂停。浏览器重新连接不会自动运动。

跨OS/浏览器、长时间录制和现场恢复仍需按 [验收](acceptance.md) 留证。工具提供LAN参数，不等于已完成全部跨平台交付验收。

## 2026-09-14 架构基线 v1

固定职责仍是：RK3588持有设备、仲裁和原始录制；Thor/condapi持有模型训练、转换及服务；开发工作站提供浏览器和离线数据整理；i2rt是唯一底层SDK。四臂/三相机的P0身份已确认，物理变更时按硬件owner复核，不重复要求非必要序列号。

P0身份、P1部署、P2相机、P3机械臂、P4模型、P5采集、P6双机合同、P7推理/HIL、P8长时验收的历史工作包见 [原始基线](archive/dagger_architecture_20260921.md)。原基线的“非RTC”“相对遥操作”等阶段限定已被当前合同取代。

## 分层与依赖方向

路径相对 `yam_abc_reproduce/`。模块依据资源生命周期划分，不依据页面按钮逐个复制实现。

| 层 / 代码所有者 | 负责 | 不负责 |
|---|---|---|
| 展示/API：`hil/static/`、`web.py`、`device_client.py` | 命令提交、状态与中文恢复指引、同源/操作会话约束 | 不构造SDK、不重算动作、不凭前端门禁替代后台检查 |
| 应用编排：`workbench.py`、`data_session.py` | 相机/设备会话、任务身份、后台录制恢复、控制屏障 | 不在HTTP超时后继续排队执行旧设备操作，不写电机 |
| 控制：`run.py`、`session.py`、`core.py`、`interaction_rules.py` | 唯一30Hz仲裁、epoch、事件优先级、维护互斥、最终动作选择 | 不等待网络、规划、编码、磁盘排空或后台服务启动 |
| 策略：`policy.py`、`policy_process.py`、`planner_process.py`、动作缓冲 | 单在途请求、数据合同、模式特有的时间对齐/动作规划 | 不拥有SDK，不自动恢复运动，不对记录回放套模型专属变换 |
| 设备：`station.py`、`robot/`；可选`executor_service.py` | SDK与CAN所有权、硬限位、反馈、实际提交 | 不拥有任务或episode，不决定模型推理与训练数据筛选 |
| 记录：`recording_service.py`、`recording.py`、`recording_process.py`、`storage.py` | episode生命周期、暂存/编码/HDF5、完整性和异常收尾 | 不改机器人目标，不在控制线程做磁盘/进程等待 |
| 离线数据：`dataset_workbench/`、`hil/recovery.py`、导出模块 | 独立任务进程、原始数据恢复、审核与转换 | 不依赖机械臂在线，不覆盖故障原件，不自动重跑不确定的导出 |

`run.py`仍是应用组合与控制循环入口，而非通用服务框架。新功能必须进入所属边界；禁止在Web、旧GUI或某个录制回调另建电机控制循环。
任务绑定与录制恢复复用 `paused_data_session`，动作接收复用共同有效性判定。测试用进程内路径不能拥有不同于生产规划进程的时效合同。

## 进程与资源所有权

默认部署：
- `yam-workstation`：独立Web/API。设备服务不可用时仍应提供故障页；不得强依赖设备服务退出而退出。
- `yam-device`：持有Workbench、Runtime和默认SDK实例；相机与机械臂会话分别连接。
- Thor通信、动作规划、录制owner、编码和预览各自独立。独立进程不代表没有CPU/内存/磁盘竞争。
- 数据集平台单独部署；后台作业由可替换的单worker进程池执行，最多4个已提交作业。

可选SDK常驻执行层：
- `yam-executor`独占四臂SDK；会话通过 `RemoteStationIO` 和租约提交。
- HOLD保持当前租约；detach/会话退出撤销租约但保留设备保持。明确的release才关闭设备。
- 上层会话不得down executor持有的CAN。租约失效拒绝旧命令，HOLD写入失败仍按硬件故障处理。
- 首次迁移要关闭旧SDK，需要现场支撑与明确许可；尚不能把离线Unix测试当作IPC迁移完成。

本项目入口共用CAN所有权边界；外部官方脚本不受本库锁约束，仍不能并行运行。SDK构造若可能已打开线程却未返回对象，不能通过抢锁假装恢复，需受控退出该持有进程。
Web更新无需重启设备；策略算法更新可在HOLD重载规划；核心仲裁或SDK实现更新仍需要受控部署，不承诺任意代码热替换。

## 产品模式与内部状态

| 模式 | 动作来源 | Leader |
|---|---|---|
| teleop | 人工、无任务也可运行、不录制 | 官方手动增益及重力/已开启SDK摩擦补偿 |
| collect | 同一人工实现，显式分集录制 | 同上 |
| inference | 模型 | 不镜像，不参与动作决策 |
| hil | 模型/人工切换，记录策略与干预 | 策略时与Follower共用最终关节目标，人工时复用遥操作 |

HOLD、TAKEOVER、HUMAN、RESUME、POLICY是内部状态，不是额外产品模式。紧急暂停由维护锁存管理；解除后仍保持。SDK反馈过期、执行异常不允许以清页面错误代替硬件故障恢复。

HIL当前顺序：
1. 页面介入：Follower保持；Leader辅助对齐，不设对齐误差门禁。
2. 右Leader①新按下沿：中止辅助对齐，复用teleop/collect的绝对1:1关节映射与夹爪软接管，不建立相对偏移。未对齐时不能承诺Follower目标不跳变。
3. 人工阶段①：锁住两侧，Leader回到高增益保持；②无功能。
4. 页面明确交还：废弃旧请求和旧计划，以新观测恢复模型；不再检查旧的0.2rad主从就绪门槛。
5. 暂停/急停优先。等待介入解锁、人工锁定等待交还两段不写训练帧，审计区间按episode重置。
6. 故障介入可明确“结束介入并切遥操作”，先保持、清干预上下文，再恢复录制；不自动开始遥操作。

Leader回零使用原生位置控制增益，运行策略镜像也使用原生关节增益；人工零Kp/Kd、SDK重力与库仑摩擦补偿仍保留。保持增益与辅助对齐归 `interaction_rules.py`；本轮不修改运动参数。

## 推理与时间合同

只有三种用户模式；均使用有限50×14绝对目标，Thor负责反归一化和delta还原，RK不重复变换。SDK关节硬限位、夹爪范围与时效检查保留；默认30Hz直接提交，不启用100Hz二阶通道。

| 模式 | 对齐与执行 | 过期处理 |
|---|---|---|
| `sync_hold` | 完整执行50步，之后保持并请求下一块；从新块第0步执行 | 请求必须仍有效；完整块执行期限从回复开始，不被异步观测年龄截掉后几步 |
| `tda_smooth` | 单在途异步预取，按请求期间实际消耗步数对齐，沿openarm-vr规则融合重叠队列 | 请求/动作年龄使用同一公共校验；不把TDA说成RTC |
| `rtc` | 30Hz tick，发送明确k和已承诺的前d个绝对目标；新块仅从k+d接管 | 不延后承诺tick；迟到/耗尽HOLD；不经过TDA或普通夹爪trick |

普通模型夹爪低值变换只用于明确模型来源；`recorded_replay`直接保留已保存的submitted_action（仍受SDK硬限位），不再做模型trick。回放进度在成功提交后推进，不按网络发出步数推进；暂停保留断点、回零重置。

epoch变化作废旧在途结果；每次恢复需要明确操作，不能把“服务重新可用”等同“继续执行旧块”。规划超时或管道损坏必须废弃旧通道；旧回复不能满足新请求。

## 故障等级与恢复合同

| 边界 | 立即行为 | 恢复入口及成功条件 |
|---|---|---|
| Thor断链/非法响应 | 清计划、HOLD、锁存policy_error、结束当前录制为aborted | 重载推理通信；就绪后只解除策略故障，显式开始才运动 |
| 规划超时/退出/错误计划 | 清计划、HOLD；关闭不可信的旧IPC通道 | 独立重载动作规划；未就绪不能启动 |
| SDK反馈/CAN/执行写入故障 | 尽可能保持并锁硬件FAULT；不自动运动 | 现场检查与受控设备恢复，不允许策略重载清除 |
| 录制/编码/磁盘错误 | 当前集aborted、HOLD；维护和明确退出介入仍可用 | 后台“恢复录制服务”：封存旧session，创建新owner，通过控制屏障安装，不重连SDK |
| 相机连接初始化异常 | camera fault，不停留在connecting | 排除依赖/设备原因后可显式重试，不宣称硬件已恢复 |
| 数据集worker退出 | 对应作业failed，归还容量，不覆盖已生成文件 | 下一次显式提交创建新worker；不自动重跑旧作业 |
| 存储未挂载 | 启用挂载约束时显示存储原因、拒绝创建/绑定录制目录 | 修复挂载后再恢复数据会话；Web须独立于NVMe程序目录 |

HOLD动作本身不代表故障已消除。策略错误与硬件FAULT分别上报；控制循环继续更新状态，页面不能用同一个全局busy/error屏蔽所有局部恢复。
耗时操作在后台；HTTP设备操作遇互斥操作立即明确拒绝，不让超时请求在锁释放后突然执行。

## 记录、恢复与数据身份

原始数据为三路MP4＋HDF5＋JSON。完整身份由task/session/episode持有；任务切换在HOLD、介入/维护结束、保存完成后执行，机械臂无需断开。

当前新设备会话仍初始化一个数据session（即使遥操作不录制帧），因此启用严格挂载约束且数据盘缺失时，也会拒绝新建设备会话；不会伪称此时能无盘重连。已连接控制不执行磁盘探测，Web诊断可独立存活。挂载检查是瞬时快照，仍须处理随后的I/O故障；系统盘上未挂载的`/data`底目录须禁止运行账号写入，防止检查与写入间的拔盘竞态。

录制失败不保证全部在途RAM数据可救；保留旧目录和错误，恢复开新session，不拼接不确定队列。候选writer初始化失败不能清掉旧故障，控制线程只交换已验证的writer引用。

离线恢复合并可解码segment与.recording-spool，按原始tick/time去重，经现有SegmentWriter生成新episode。源文件不改；坏pickle、半写文件、缺图逐项报告；缺manifest不猜fps和数据身份。恢复重新编码，不能冒充原始字节复制或无损补回未落盘帧。

HIL等待过滤后的训练时间为连续frame_index/fps，原始tick/time保留供审计；两种等待区间摘要每集重置。字段详见 [转换合同](convert.md)，公共合同变化必须覆盖采集与数据集两端。

## 部署、验证与维护规则

- 兼容unit与可选系统盘运行时模板归 [环境](environment.md)。系统盘保存程序/虚拟环境/配置和诊断入口，NVMe保存原始数据；迁移前验证真实挂载，不能直接移动带绝对路径的venv。
- 原始录制位置配置在边界校验，不放进30Hz tick；缺盘不允许偷偷mkdir到系统盘。
- 上游GUI和部署入口为legacy，保留兼容用途及明确提示，不继续在那里复制四模式工作流。
- Python安装产物必须包含两平台静态资源及ABC schema；源码可运行不等于wheel可交付。
- 注释说明资源归属、线程/进程边界、时钟域、单位、异常恢复条件；避免解释显而易见语句。架构正文保持唯一当前合同，历史只在archive/evidence。
- 回归必须包含真实子进程故障、超时迟到、候选启动失败、前后端门禁一致、数据回读和拒绝自动恢复运动；mock与真机分别记录。
- 本轮不自动部署、不关闭机械臂、不改变增益、补偿、模型或三种推理算法。现场迁移需另行确认，验收结果归 [验收边界](acceptance.md)。
