# 项目工作汇报｜2026-09-17

## 项目名称

YAM 机器人设备、数据采集与 Thor 推理平台。RK3588 IPC 负责四根机械臂（两根 Follower、两根 Leader）、三台 D405 相机、控制时序和原始数据记录；Thor 负责策略推理；采集工作台和数据集工作台负责现场调试、数据审核与导出。

## 已完成工作

1. **完成设备控制与动作规划的进程拆分。** 普通策略的动作块规划、TDA 队列处理和同步 50 步规划移入独立的 `yam-action-planner` 进程，`yam-device` 保留机械臂 SDK 独占权、状态机、安全限幅和动作消费。设备控制循环不再等待 Thor；规划进程只允许在 HOLD 且未录制时重载，设备侧还会复核请求版本、时效和动作来源。专项测试 49 项通过，全量测试 355 项通过、3 项跳过、17 项子测试通过。现场验证四路 CAN 可用、四臂反馈龄约 0.5–5 ms，规划进程可以在 HOLD 下独立重载而不改变设备进程和机械臂状态。

2. **完成普通推理的无跨块融合部署。** 按现场要求将测量模式切到 `raw`，新动作块在同一目标时刻直接接管，不再默认使用整段重叠融合、短过渡或 100Hz 二阶轨迹；同时保留观测时间对齐、夹爪 `[0,1]` 限幅和故障进入 HOLD。针对旧同步记录，确认反馈相对目标包络曾改写大量模型目标，因此从 30Hz 直达路径移除该层反馈相对裁减，仍保留 SDK 硬限位、夹爪限幅和故障保护。相关专项和全量回归通过，并完成 IPC 静止态部署核验。

3. **完成训练式 RTC 的端到端控制接入准备。** 固定 Thor 地址 `ws://192.168.250.1:8000`，统一 30Hz、H50、14D 和最多 10 步承诺前缀的协议合同；3588 侧补齐 observation tick、目标起始 tick 和已提交动作起始 tick 的对应关系。新增控制时间轴、已提交前缀复用、未来前缀 SDK 限位、预定接管时刻接收以及迟到结果丢弃逻辑。IPC 在保持四臂 HOLD 的情况下完成通信子进程切换，页面能够显示 RTC 模式和延迟步数，未因切换释放机械臂。

4. **完成首次 RTC 真机短测的问题定位和控制端修复。** 首次运行出现 `invalid policy response` 并进入 FAULT；记录显示第一条回复晚到 2 个控制步，第二条回复按时到达但右夹爪有限预测最大约 1.025。问题根因是控制端先执行 SDK 严格校验、后做夹爪限幅，已改为先将夹爪裁到 `[0,1]` 再进行 SDK 限位和校验，同时补充故障录制的 `aborted` 收尾。页面连接后的右侧夹爪故障已完成修复，后续需要验证的是完整 RTC 运动闭环，而不是继续把该故障当作未解决问题。:codex-annotation{index="1"}

5. **完成 Thor RTC 候选检查点和低延迟路线验证。** 30000 检查点完成参数交接、FP32 转换、JAX/PyTorch/TensorRT 对照及固定地址协议 smoke；7 步候选在 Thor 本机固定地址下 9/9 通过，服务与本机往返 P50 约 194–195 ms。晚间复核发现训练使用分位数归一化，而旧 RTC 服务和参考实现错误使用均值/标准差，随即停止服务并保留原始容器和证据。按正确分位数重新计算后，9 例 JAX 与 TensorRT 的最大单关节差约 0.00452 rad，现场动作交界最大值由约 2.505 rad 降至约 0.104 rad；这完成了事故定位和离线复测，不代表新版服务已经重新上线。

## 当前问题

1. **RTC 服务暂时停用。** 前缀归一化错误会改变已承诺动作条件，旧的 10 步、7 步服务结果和此前延迟记录不能作为当前可用性结论。正确归一化版本尚未完成重新部署、跨 IPC smoke 和真机运动验收。

2. **首次 RTC 现场 episode 未形成有效任务结果。** 第一条回复迟到，第二条虽修复了夹爪越界路径但本次会话已进入故障并中止录制；`d=8` 在现场没有余量，已暂定默认 `d=9`，但还没有基于真实曝光、控制 tick 和运动反馈的联合测量。

3. **IPC 硬件稳定性仍是现场前置条件。** NVMe/PCIe 间歇枚举、`/data` 挂载和 USB-CAN/反馈过期问题仍没有统一根因；9 月 17 日完成的是 HOLD 和静止态验证，不能据此推断运动中的 CAN、存储、相机和长时间运行已经稳定。

4. **普通推理效果和录制吞吐仍未完成验收。** `raw`、TDA 和同步模式尚未在同一任务、同一初始状态下完成公平运动对照；真实任务成功率、夹爪闭合效果和运动中 30Hz 长时录制也没有形成可交付结论。

5. **数据平台交付闭环仍需收口。** 采集工作台的设备调试入口已经明确，但数据集工作台 8767 的局域网跨平台访问、真实数据导入审核导出、失败集恢复和长期数据版本管理还没有完成现场验收。

## 下一步计划

1. 按正确分位数归一化重新构建并审计 RTC 服务，先做本机协议和 IPC 无电机验证，再由现场人员在 HOLD 下确认 `d=9`，随后进行短时、可停止的 RTC 运动复验；记录迟到率、丢弃率、实际提交目标、反馈龄和故障收尾。
2. 在继续运动前稳定 IPC 的 NVMe/PCIe、供电、USB Hub 和 USB-CAN 链路，确认 `/data` 持续挂载、四路 CAN 可重复拉起、三台相机启动后状态龄受控。
3. 使用同一任务和同一初始姿态，对 `raw`、TDA 和同步动作规划做短时对照，保留 SDK 硬限位与故障 HOLD；重点检查动作块切换、夹爪近期目标和真实墙钟调度，不用离线差异替代任务效果。
4. 继续压测 NVMe 临时暂存和独立录制进程，完成运动中 30Hz 长时写入、异常停止、空间不足和 HDF5/视频回读验证，避免通过扩大内存队列掩盖吞吐问题。
5. 完成 8767 数据集工作台的局域网端口和跨平台浏览器验收，打通真实 episode 的分类、审核、恢复、导出和回读；同时保留训练检查点、归一化文件与推理服务的可追溯绑定。
